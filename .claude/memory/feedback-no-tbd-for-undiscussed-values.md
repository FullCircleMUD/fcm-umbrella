TBDs are wanted when they are meaningful — they stop a session writing an undiscussed point as settled. Before placing one, think twice: is this a real open issue, or something I have invented or am assuming?

If unsure, ask: "I've got this issue — should it go on the TBD list?" Tim can say "yes, not dealing with that now, TBD it" or wave it off.

**A resolved TBD disappears.** If the answer changes the code, the code records it; if not, there is nothing to record. A genuinely important fact belongs in the component's normal docs, and usually already is — keep a line only when it is not. No "this was asked and decided" trail.

**Why:** 2026-09-25, a core_actor_stats "[TBD — the default pool maxima]" had never been discussed, and a durability "[TBD — colour codes]" was answered in one line. Vacuous TBDs and decision records lower the worth of the documentation.
